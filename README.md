## Implementation overview

1. **Trie construction.** All patterns are inserted into a trie. Each node stores 128 transitions (ASCII). The node where a pattern ends stores that pattern in a linked list (`outHead` / `outNext`), so duplicate patterns are all reported.
2. **Failure links.** A breadth-first traversal computes `fail[v]` for every node: the node of the longest proper suffix of `v`'s string that is also a prefix of some pattern. While doing so, missing transitions are filled in using `go[u][c] = go[fail[u]][c]`, turning the trie into a complete deterministic automaton. The search loop therefore never follows failure links explicitly, and each text character costs exactly one array lookup.
3. **Output (dictionary) links.** `dictLink[v]` points to the nearest node on the failure chain that ends a pattern. When a state is reached, only nodes that really end a pattern are visited, so the cost of reporting is proportional to the number of matches, not to the length of the failure chain.
4. **Search.** The text is scanned once from left to right. After each character the automaton moves to the next state and all patterns ending at that position are reported through the dictionary-link chain. Overlapping and nested matches are all found.

Public API: `search(text, listener)`, `findAll(text)`, `countMatches(text)`, `occurrenceCounts(text)`.

Limitations of this implementation: patterns must be non-empty ASCII strings; non-ASCII characters in the text are treated as separators (the automaton resets to the root).

## Experimental setup

* Pattern counts: 10, 100, 1,000.
* Text lengths: 1,000, 10,000, 100,000 characters.
* Two data scenarios (random data, fixed seed 42):
  * DNA-like: alphabet `acgt`, pattern length 6–10 (many matches and many partial matches).
  * Lowercase English letters: 26 symbols, pattern length 4–8 (fewer matches).
* Each case: 30 unmeasured warm-up iterations (JIT), then 5 measured runs; the average is reported.
* Aho–Corasick time = construction + search. KMP time = prefix-function construction and search for every pattern, one after another.
* Both algorithms count overlapping matches, and the benchmark aborts if their match counts differ, so every reported row is also a correctness check.

## Complexity analysis

Notation: `n` = text length, `k` = number of patterns, `M` = total length of all patterns, `σ` = alphabet size (128 here), `z` = number of reported matches.

| Phase | Aho–Corasick | KMP, one pattern at a time |
|---|---|---|
| Preprocessing | `O(M·σ)` for the full automaton (`O(M)` with sparse transitions) | `O(M)` in total |
| Search | `O(n + z)` | `O(k·n)` in total |
| **Total** | **`O(M·σ + n + z)`** | **`O(M + k·n)`** |
| Extra space | `O(M·σ)` (`O(M)` sparse) | `O(max m_i)` at a time |

Why the search is `O(n + z)`: every text character causes exactly one transition, and every dictionary-link step reports a real match. Why construction is linear in `M` (times `σ` for the dense table): each trie node is enqueued once in the BFS and processed in constant time per symbol, and the failure and dictionary links are derived from the already-computed values of shallower nodes.

Space: the trie has at most `M + 1` nodes. With the dense 128-entry transition table, memory is about `M · 128 · 4` bytes plus small per-node arrays. In the experiments, 1,000 patterns produced 3,928 nodes (DNA-like) and 4,537 nodes (English), which is about 2–2.5 MB. A map-based or sorted-edge representation would reduce this to `O(M)` at the price of slower transitions.

## Roles of the trie and failure links

* **Trie.** Merges common prefixes of all patterns into a single structure, so every pattern is "in progress" simultaneously. A trie state represents the longest suffix of the text read so far that is a prefix of some pattern.
* **Failure links.** Generalise the KMP prefix function to a trie. When the next character cannot extend the current state, the failure link jumps to the longest proper suffix that is still a prefix of some pattern. No text character is ever re-read, which is what gives linear time.
* **Dictionary links.** Skip failure-chain nodes that do not end a pattern, so patterns that are suffixes of other patterns (for example `he` inside `she`) are reported efficiently.

## Why Aho–Corasick suits multi-pattern search

The text is scanned once regardless of the number of patterns, and all patterns are matched simultaneously. The running time depends on the text length and the number of matches, not on `k`. Typical uses: intrusion detection, antivirus signature scanning, profanity and keyword filtering, DNA motif search, and `fgrep -f`.

## Discussion of results

* **Aho–Corasick is faster in every case.** The KMP / AC ratio ranges from 1.45x (10 patterns, 1,000 characters, English) to 284.52x (1,000 patterns, 100,000 characters, DNA-like). Over all 18 cases the Aho–Corasick total time stays between 0.03 ms and 4.3 ms.
* **KMP time grows with both k and n.** For 1,000 DNA-like patterns it takes 7.4 ms, 81.8 ms and 827 ms for texts of 1,000, 10,000 and 100,000 characters, about 10x per 10x of text. On the 100,000-character text, going from 10 to 100 to 1,000 patterns raises KMP from 11.1 ms to 80.9 ms to 827 ms, i.e. roughly proportional to k, as O(k·n) predicts.
* **Aho–Corasick search time depends mainly on n.** On 100,000 characters the search takes about 0.7–1.5 ms in all scenarios, roughly 7–15 ns per character, and it grows about 10x per 10x of text (for example 0.0918 ms to 0.7751 ms for 100 DNA-like patterns). The small increase for 1,000 patterns is explained by a larger automaton (about 4,000–4,500 nodes with a 128-entry row each, a few MB, which fits the CPU cache less well) and by more reported matches.
* **Construction dominates on short texts.** Build time grows with the trie size (56 nodes: about 0.02 ms; 4,537 nodes: about 1.1–3.1 ms) and exceeds the search time for 1,000-character texts. This is why the advantage is smallest (1.45x–6x) there. The dense table makes building cost O(M·σ).
* **Number of matches.** The DNA-like scenario produces far more matches (up to 5,767) than the 26-letter scenario (up to 65), but z stays small compared with n, so both scenarios are dominated by the O(n) scan.
* **Measurement noise.** Sub-millisecond timings still fluctuate (for example, the build time of the same 10-pattern trie differs between the 1,000 and 10,000-character cases), so trends across rows are more reliable than individual cells.

## Advantages and limitations

**Aho–Corasick**
* (+) Single pass over the text, time independent of `k` apart from the output size.
* (+) Finds all overlapping and nested matches, with predictable worst-case time (no hidden quadratic behaviour).
* (+) The automaton is built once and reused for many texts.
* (−) Higher preprocessing cost and memory (`O(M·σ)` dense), poorer cache behaviour for large automata.
* (−) Less convenient for dynamic pattern sets (adding a pattern requires rebuilding the links) and for a single pattern, where KMP is simpler and lighter.

**KMP per pattern**
* (+) Very small memory footprint (one prefix table), trivial to implement, no preprocessing shared between patterns.
* (+) Good for one or a few patterns, or when patterns change constantly.
* (−) `O(k·n)` total time: the text is rescanned for each pattern, which becomes expensive for hundreds or thousands of patterns.

## Testing

`AhoCorasickTest` covers: the classic `he / she / his / hers` example, overlapping and nested patterns, duplicate patterns, empty text and no matches, single-character patterns, exact match positions, non-ASCII text, invalid input, and 200 randomised comparisons against KMP. In addition, the benchmark verifies that Aho–Corasick and KMP report the same number of matches in all 18 experiments.

## Possible improvements

* Sparse or compressed transitions to cut memory to `O(M)`.
* Case-insensitive matching and Unicode support via a character map.
* Streaming search that keeps the automaton state across chunks.
